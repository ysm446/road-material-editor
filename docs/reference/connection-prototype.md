# 道路・沿道の接続試作（P0）

作成日時: 2026-09-07 15:10
更新日時: 2026-09-07 15:31

## 何を確認する試作か

水平な直線道路を入力に、砂利路肩→舗装の横方向の移行と、舗装→砂利道の進行方向の移行を同時に生成する。
左側には幅2 m・高さ15 cmの仮歩道を置く。歩道は単色のコンクリート平板として、1.5 m間隔に幅12 mm・深さ4 mmの目地をメッシュで作る。
目地の縁には斜面を設け、目地の標本位置を全パネルで共有する。歩道の画像素材は不要。

`ConnectionPrototype.cpp` が道路の座標を読み、一つの地表と縁石の立ち上がり・歩道天端を生成する。
左右と進行方向の被覆率を共通関数で決め、重ねた地表メッシュで継ぎ目を隠さない。
縁石の稜線は法線を分けても位置と断面 UV を一致させる。変位は同じ座標から世界 Y 方向へ行う。
生成サンプルの舗装・砂利・歩道はそれぞれ 0.015 / 0.08 / 0.005 m のハイト倍率。Road / Shoulder入力は元の変位量を使う。ハイト0.5が変位0の基準なので、これらは最大突出量ではない。
試作の法線合成は共通の断面接空間で RNM を使用する。

## 起動

既存プロジェクトから材質 ID を指定し、検証用コピーを作る。入力ファイルと素材は変更しない。
コマンドのパスと ID は手元のデータへ置き換える。

```powershell
$sourceProject = 'path/to/source.tgproj'
$testProject = 'data/connection-prototype/prototype.tgproj'
$asphaltMaterialId = 4
$gravelMaterialId = 2
python tools/make_connection_prototype.py $sourceProject $testProject --asphalt $asphaltMaterialId --gravel $gravelMaterialId

$appExe = 'build/bin/Debug/road_editor.exe'
& $appExe --project $testProject --connection-prototype 10 3 5
```

`10 3 5` は生成スクリプトが作る Road / 砂利 Surface / 仮歩道 Surface のノード ID。
通常のプロジェクトにも有効な ID を指定できるが、形状を作るRoadは水平な直線・長さ50 m以内が対象。接続先はSurfaceのほかRoad / Shoulderの材質構成を指定できる。
`--connection-prototype-flat` を加えると GPU 変位だけを止め、15 cmの段差と目地のメッシュは残す。
`--screenshot` / `--screenshot-ui` で書き出せる。通常起動では従来のグラフをそのまま評価する。

試作の生成寸法は `ConnectionPrototypeSettings`、素材は指定ノードの Surface を使う。
大きな UI はまだ作らず、描画・生成方法の検証を優先している。
保存されるのは入力グラフであり、試作の派生メッシュや起動オプションはプロジェクトへ保存しない。
試作を再表示するときも上記オプションを付ける。

## 手元素材と追加素材

手元のアスファルトと Gravel Ground の Base Color / Normal / ORD のハイトを使用できた。
歩道は仮メッシュと単色材質を使うので、試作のための追加素材は必須ではない。
本番の見た目を詰める段階では、新舗装・荒れた舗装・砂利／土・草地があると比較できる。
各素材は Base Color / Normal / Roughness / Height が望ましく、AO は任意。
Normal の規約、パック画像のチャンネル、反復する実寸（例: 2 m四方）、分かればハイトの実寸範囲を添える。
既存の画像形式を使い、ハイトは可能なら16bit以上。高解像度の用意を先に必須にせず、まず2K程度で確認する。
素材は `data/` に置く。生成コピーは元の画像の絶対パスを参照するため、別のPCへ渡すときは素材も再リンクする。

## 複数レイヤーの検証

生成時に `--layered` を加えると、4層の舗装Roadと4層の砂利Roadを作る。起動時は `--connection-prototype 10 30 5` を指定する。
砂利用Roadは材質構成の入力として使い、その形状は描画しない。仮歩道と合わせて9層を評価する。
同じ実素材を異なる反復長で参照し、轍・長さ方向ノイズ・端のマスクと高さ条件が接続後にも残るかを確認する。

各組の下地・追加3層・Road Mask・UV反復・道路UVの向き・ワールドUV指定・高さ条件・混ぜ方・変位量を保持する。
まず各組の重みを求め、その結果を共通の横／進行方向マスクで合成する。変位も同じ組と接続マスクを使う。
舗装の横原点は砂利帯の幅だけずらし、元の道路内のUVとマスク位置を維持する。接続先は試作断面の原点から配置する。
接続先の独立した区間開始位置や長さへの自動適合はまだ行わず、範囲外のマスクは端をクランプする。

P0内部では形状のない材質評価専用SceneMeshエントリを3個持ち、既存の評価器・テクスチャアップロード・GPU遅延解放を使う。
実際に描画・変位するメッシュは共通面1個だけ。P1の保存資産や最終的なプリセット型ではない。
CPU/HLSLの定数構造は192 bytesの組を3個追加し、通常道路と試作でレイヤー重みの計算を共用する。
ハイト表示は接続後の実寸変位を0.5基準で表示する。ローカルハイト表示の試作半径は2 cm。

## 検証と限界

- Debug ビルドと全CPUテストが成功。二方向の被覆、15 cmの天端と側面、4 mmの目地、稜線の位置・UV一致、決定性、不正寸法・非水平入力の拒否を確認する。
- MeshPbr の VS / PS / DS は DXC 単体コンパイルを実施。起動時には HS 等もコンパイルされる。
- 確認資料は `data/connection-prototype/`。`prototype.png` は全体、`close.png` は変位あり近景、`flat.png` は変位なしの同じ視点。
- 上記3画像を目視し、舗装と砂利の移行・歩道の立ち上がりに目立つ隙間が無いことを確認。細い目地は遠景でサブピクセルになり、点状に見える箇所が残る。
- 最終試作の24 m道路は13,904頂点、12,956三角形、共通マスク1,572,864 bytes。DebugのCPU生成は3回で24.86〜25.30 ms（GPUの評価・描画時間は含まない）。起動ログに警告・エラーの出力は無し。
- 4層＋4層＋歩道1層の描画を `layered.png` と近景 `layered-close.png` で目視確認。歩道の付け根に目立つ隙間は無い。試作オプションなしの `ordinary-layered.png` でも通常道路の描画を確認。3回の起動ログに警告・エラー無し。CPUテストでは各組のマスク・全追加層・UV・高さ条件・変位の保持と不正な構成参照の拒否を確認。
- 9層構成も13,904頂点、12,956三角形。マスク合計2,359,296 bytes、DebugのCPUコンパイル206.73 ms（1回、元Roadの評価とマスク焼き込みを含む）。初回起動から16フレーム目の画像出力まで約69秒。これは素材読込・シェーダー／パイプライン準備を含み、GPUフレーム時間ではない。
- 曲線・勾配・バンク、区間編集 UI、部品アセット一覧、標示・Decal の追従、保存資産化は未対応。
- 歩道の始終端を閉じる端部部品や目地幅の自動配分も未対応。今は連続断面と目地の検証用。
- 境界の揺れは解析的な仮模様。舗装端の欠け・砂だまり等の仕上げは次に評価する。
- 生成時間と頂点・三角形・マスク量をログに出す。GPUフレーム時間・総VRAMの計測と、GPU変位後の境界誤差0.1 mmの数値検証は未実施。

P0全体の完了とは区別し、この試作の結果を踏まえてGPU負荷・境界誤差の計測と曲線上の共通変位へ進む。
