# プリセットと配置記述の保存基盤（P1 第一段）

作成日時: 2026-09-07 16:13
更新日時: 2026-09-08 01:44

## 現行形式

現在はプロジェクト版22・配置節版5。境界アセットは `boundaryMaterials`、沿道の割当は `boundaryMaterial` で保持する。[境界仕様](boundary-materials.md) を参照。材質は独立した `layerMaterials` に置き、形状プリセットは `layerMaterial` IDで参照する。[現行の契約と移行](layer-material-assets.md) を参照。以下は導入時の記録で、埋込材質の説明は旧版1〜3に対応する。

## 今回の範囲

プロジェクトに埋め込むプリセットと道路・沿道の配置を、GPUリソースを持たない編集データとして追加した。
`Application` が `SurfaceLayoutDocument` を所有する。シーングラフは道路の形状を持ち、配置側はそのRoadノードIDを参照する。
`ProjectRefs` と `DocumentSnapshot` に含め、保存・読み込み・Undo/Redo・新規プロジェクトへの切替で保持または初期化する。

通常起動でも配置されたRoadの材質を評価する。Roadプロパティの最小区間UIから配置を作成・編集できる（[試用手順](road-surface-editor.md)）。開発用の `--surface-layout-preview <Road ID>` で、保存した道路本体の区間を材質プレビューに適用できる。
専用プリセットグラフ、公開パラメータの評価先への結線、接続上書きと沿道の配置編集UIは未実装。
P1全体の完了とはせず、まず共通のID・断面・区間・公開値を失わず保存できる基盤を確立する。

## データの契約

- IDは文書内で共通の32bit正整数。プリセット・断面点・公開パラメータ・配置・帯・区間を通して一意にし、`nextId` より小さい値を使う。ノードID・素材IDとは別の名前空間。枯渇時は0を返して再利用しない。
- プリセットは名前・役割・版1・変位量・断面点・四端の境界条件・最大4個の素材参照・公開パラメータを持つ。素材未指定は定数色と粗さを使う記述として保存する。
- 断面は横位置と高さをメートルで持つ。横位置の同値は縁石の垂直面に使える。逆順と連続する同一点は拒否する。
- 境界条件は内端・外端・始端・終端の順。混在／段差保持／固定、移行幅、許容高さ調整、輪郭保持の意図を保存する。接続相手別の組み合わせ表は作らない。
- 各RoadLayoutはRoadノードIDを一つ参照し、道路本体の帯を必ず一つ持つ。左右は複数の帯を許可し、同じ側はRoadから近い順に並べる。Roadに二重のLayoutを割り当てない。
- 区間は0〜50 m、開始より終了が後、開始順・重複なし。帯ごとに区切りを独立させる。隙間は保存可能で、未配置領域の処理は評価段階で定める。
- 区間の公開値は定義IDを参照し、始点値・終点値を範囲内で保存する。道路帯には道路用、左右の帯には地面／歩道用のプリセットを使う。

## 読み込みと編集の整合性

`.tgproj` の版を17へ上げ、ルートに `surfaceLayouts` を追加する。導入時の節の版は1。現在はプロジェクト版18・節の版2を保存する。
版16以前で節が無い場合は空の配置として読み込む。版17以降で節が欠けている場合、未対応版、型違い、重複ID、参照切れ、非有限値、重複区間は現在の文書を置き換える前に拒否する。
素材参照は既存のプロジェクト素材と同じ保存IDへ付け替え、読み込み時に実行時IDへ戻す。存在しない素材は既存Surfaceと同様に未指定の0にする。

配置先Roadの存在と種類も保存前・読込前に検査する。UIでRoadを削除した場合は、そのRoadの配置を同じ編集で削除する。UndoはRoadと配置を一緒に復元する。
参照切れのRoad IDを再読込後に別ノードへ再利用して、意図せず接続し直す状態を作らない。
安定ID・断面・公開値は値としてスナップショットに含める。素材の復元後に参照を確認する。

## 検証用コピー

既存の生成スクリプトに `--layout-description` を付けると、道路3種・沿道3種の記述を追加した版18のコピーを作る。
素材は手元の舗装・砂利と定数の仮歩道を再利用する。草地・荒れた舗装の専用素材や描画まで用意したものではない。

```powershell
$sourceProject = 'path/to/source.tgproj'
$testProject = 'data/connection-prototype/layout-v17.tgproj'
$asphaltId = 4
$gravelId = 2
python tools/make_connection_prototype.py $sourceProject $testProject --asphalt $asphaltId --gravel $gravelId --length 50 --layered --layout-description
```

50 mでは道路を0 / 12 / 28 / 50 m、沿道を0 / 17 / 35 / 50 mで区切る。公開値の始終端を0.2→0.8で保存する。
生成メッシュと混合マスクは保存せず、評価時に再構築する。道路形状は既存Roadから生成する。

## 確認結果

- Debugビルドと全CPUテストが成功。6プリセット・独立区間・始終端値のJSON往復、参照・型・ID・寸法の拒否、Undo/Redoを確認した。
- 実アプリで版17を読み込み→保存→再読込→再保存し、JSON全体が一致した。素材ID4/2が保存ID1/2へ正しく付け替わった。資料は `data/connection-prototype/layout-roundtrip-*.tgproj`。
- 版16の試作を読み込んで版17へ保存し、空の配置データを持つことを確認した（`legacy-upgraded-v17.tgproj`）。
- 保存試験中、材質サムネイルの初回UAV書込みでCOMMONレイアウトのGPU検証エラーを観測した。初期化をDiscardから明示的なRTVクリアへ変更し、作成時の最適化クリア値にも合わせた。修正後3回の起動で警告・エラー無しを確認した。

最終確認は `layout-final-1.tgproj` と `layout-final-2.tgproj` のJSON全体が一致。`layout-final-ui.png` で道路と材質サムネイルを目視確認した。UIからのプリセット編集はまだ無いため、Undo/RedoはCPUの文書スナップショットテストでの確認。

## 区間の評価と道路本体のプレビュー

`SampleSurfaceBand` は検証済み文書の一つの帯を実距離で評価し、区間ID・プリセットID・混合率・公開値を返す。道路と左右の帯は独立して呼び出す。

- 接する区間の境界を、前区間の `blendOut` だけ手前から次区間の `blendIn` だけ先までsmoothstepで移行する。
- 各側の移行距離はその区間長の半分までに抑える。短い区間でも前後の移行が交差せず、同時に最大2区間、被覆率の和は1となる。元の保存値は変更しない。
- 空白区間と範囲外は空の結果を返す。距離0の移行は次区間へ切り替える。最後の終点だけは最後の区間に含める。
- 公開値は実距離で線形補間し、移行で区間外へ参照した部分は端値を使う。指定が無ければ既定値を返す。評価先への結線はまだ行わない。

開発用プレビューは道路全長を覆う空白のない区間列、最大3種類、各プリセット4素材に限定する。不完全な区間列はエラーにする。同じプリセットを複数区間へ再配置できる。
道路を分割せず、1本のRoad形状と実距離の混合マスク、プリセットごとの既存材質評価コンテキストを生成する。素材参照・定数色・粗さ・UV反復長と向き・ワールドUV・変位量を評価器へ渡す。法線合成は既存のRNM経路を使う。

```powershell
$app = 'build/bin/Debug/road_editor.exe'
$project = 'data/connection-prototype/layout-v17.tgproj'
$roadId = 10
& $app --project $project --surface-layout-preview $roadId
```

このオプションは道路本体の材質確認専用。沿道・標示・断面変更・四端のBoundaryContract・公開値の結線は描画しない。通常起動と道路本体のUIは統合済み。沿道との二方向接続と専用プリセットグラフは後続。保存形式の変更はない。

単層プレビュー導入時の区間評価はDebugビルドと全テストが成功。独立した帯、短い区間、空白、0距離の切替、公開値の既定値と補間、素材参照と変位量、未対応の多層材質の拒否を確認した。実素材の `layout-preview.png`（移行0）と `layout-blended.png`（移行あり）で表示の違いを目視し、両起動ログに警告・エラー無し。資料は `data/connection-prototype/`。Releaseと曲線の描画、UI操作は今回未検証。

3種類の定数色による `layout-colors.png` でも両境界の連続移行を目視確認した。この起動も警告・エラー無し。

## 多層プリセット（プロジェクト版18・配置節版2）

プリセットの `materials` を下地から上へ最大4層として評価する。`layerBlendRange` はプリセット内のハイト合成幅。区間間の移行距離とは別に保持する。
各層はPBR素材参照・定数色・粗さ・金属度・AO・UV反復長・ワールドUV・混ぜ方（0=マスク、1=ハイト競合）・高さ条件（0=無し、1=高い所、2=低い所）としきい値／柔らかさを持つ。

上層の `mask` に既存Road Maskの全設定を埋め込む。形はWheelTracks=0、EdgeFalloff=1、LengthNoise=2、Constant=3、WorldNoise=4。側はBoth=0、Left=1、Right=2。
車線からの轍位置、幅・間隔・ぼかし、ノイズのスケール・種・しきい値、長さ方向のムラ、強さ・反転を保存する。マスクは道路全体の実距離・車線・世界座標から既存の `BakeRoadMask` で再生成し、GPUテクスチャは保存しない。

下地にはマスク・高さ条件・混ぜ方を指定しない。上層のmaskがnullなら未結線として被覆0。節版1のファイルは追加設定を既定値とnullで補い、既存の単層表示を維持する。節版2は追加キーの欠落、未知のenum、非有限値・範囲外を拒否する。旧アプリが新しい層設定を無視して上書きしないよう、プロジェクト版も18に上げる。

`--layout-description --layered` で道路3種それぞれに4層を持つ検証コピーを作れる。区間の移行と各プリセット内部のマスクを別々に評価し、既存のRNMと変位経路で合成する。
公開値の評価先への結線、区間ごとの種の反映、沿道断面・境界条件の解決は後続。この段階のマスク座標と種はプリセット内の設定を使う。

多層対応の検証: Debugビルド・全テストが成功。既存Roadと同じマスク生成、各層設定の保存往復、不正値の拒否、マスク編集のUndoを確認した。実素材の3種×4層を `layout-layered-v18.png` で目視確認。`layout-v18-save1.tgproj` と `layout-v18-save2.tgproj` はJSON全体が一致し、全層の素材IDの付け替えも確認した。資料は `data/connection-prototype/`。Release・曲線の描画・UI操作は今回未検証。

版17の実ファイルも版18へ移行し、既存スロットの全設定が維持され、新項目が既定値で補われることを確認した（`layout-v17-upgraded.tgproj`）。プレビューと保存・移行を含む4回の起動ログに警告・エラー無し。

通常描画では道路帯が空の場合に元のRoad材質を使う。これをUIでの解除状態とし、沿道の記述は削除しない。配置先の道路と白線などの生成順序・参照番号は保持し、材質コンテキストだけをシーン末尾へ追加する。
